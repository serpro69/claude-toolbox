## Repository context

Read this section first if you have not worked in this repository.

- **Canonical source and generators.** `klaude-plugin/` is hand-authored. `make generate-kodex` (a Go tool in `cmd/generate-kodex/`, driven by `scripts/kodex-generate-manifest.yml`) produces `kodex-plugin/` and `.codex/agents/`. `make generate-guard` (`scripts/generate-guard.sh`) projects `klaude-plugin/scripts/guard/guard-rules.json` into several targets and copies the guard engine. CI rejects stale generated output (`.github/workflows/generated-check.yml`). Never edit a generated copy.
- **The guard.** `klaude-plugin/scripts/guard/guard.sh` picks an interpreter and runs `run-guard.py` under isolated Python (`python3 -I`), which loads the adjacent `guard.py` by absolute path. The engine is standard library only and stays within Python 3.8 syntax. A denial is exit 2 with a reason on stderr; any failure denies. Policy is anchored by `KK_GUARD_PROJECT_ROOT`; project additions come from `<root>/.claude/kk-guard.json`.
- **Codex adapters today.** `.codex/scripts/pretooluse-{bash,patch,mcp}.sh` are hand-authored and registered in `.codex/hooks.json`. They derive the project root from their own location. `.codex/scripts/session-start.sh` injects instructions.
- **Template sync today.** `.claude/toolbox/scripts/template-sync.sh` fetches the template at a version, applies substitutions from `.github/template-state.json`, compares, and applies. It has a migration pattern (`needs_*` / `run_*` pairs gated on `APPLY_MODE`), a three-way settings merge with a fetched base, and a hook filter that separates toolbox entries from downstream ones. Three facts about it shape the migration work. Both `--local` and the downstream workflow's `--apply` reach `apply_changes`, so anything gated only on `APPLY_MODE` runs from an ordinary sync. Since v0.21.0, `handoff_to_upstream_script` replaces the running script with the target version's copy before anything changes except the manifest, which `migrate_manifest` and `backfill_manifest_variables` may rewrite first. The downstream workflow has fetched the target version's copy before running since v0.5.0. The settings merge in `apply_substitutions` assigns `permissions.deny` from upstream and re-applies the manifest-controlled keys after merging.
- **Tests.** Shell suites are `test/test-*.sh` and share `test/helpers.sh`. Python suites run through a thin shell wrapper under isolated Python (see `test/test-guard.sh` and `test/guard/test_guard.py`).
- **Vendor versions.** The design's evidence is from Claude Code 2.1.296 and Codex CLI 0.169.0. Record the versions with every probe.

Two conventions apply to all new `kk` code:

- **Python 3.8, standard library only, run isolated.** Follow the guard's loader pattern for importing sibling modules; isolated mode does not put the script's directory on the import path.
- **Vendor CLIs are stubbed in tests.** Put fake `claude` and `codex` executables first on `PATH`; they record their arguments and print canned JSON. Live vendor behaviour belongs in recorded probes, not in the test suites.

Record probe evidence under `docs/feat/wip/machine-level-delivery/verification/`, one directory per task, with the tool versions, the commands and the observed output.

The work is ordered so that the two probe tasks run first. Either can change the design; do not start the tasks that depend on them until their results are recorded and the design is updated.

## Codex vendor probes

These settle the source-read claims in [Evidence and provenance](design.md#evidence-and-provenance). Use a scratch `CODEX_HOME` so the real one is untouched. Runs that need a model call need credentials in the scratch home; the maintainer copies them, the implementer does not.

An *open session* means one long-lived Codex process. A resumed `codex exec` starts a new process and reloads plugins, so it proves nothing here. Drive the interactive TUI in a tmux pane: send a prompt, change the installation from another shell, send a second prompt, capture the pane.

To attribute a denial to the guard, the probe hook writes a log line for every call it sees, and the session runs with a sandbox that would otherwise permit the action.

1. Build a scratch local marketplace with two plugins: one skills-only, one with a `PreToolUse` hook that denies a marker command. Install both and trust the hook. → verify: a marker command is denied and the hook log shows it.
2. With a session open, re-add only the skills plugin at a new version, then send a marker command in the open session. → verify: the hook log shows a new denial. This is [assumption 1](design.md#assumptions).
3. Re-add the unchanged guard plugin and check whether its cache directory was replaced. Then install it once under a digest-stamped version string of the kind `kk` would give a local checkout. → verify: record whether the directory's identity changed, which decides whether `kk` must skip unchanged guards; record whether Codex accepts the stamped string as a version and a cache directory name, and which form it accepts (assumption 13).
4. With a session open, re-add the guard plugin at a new version with a changed script, then send a marker command. → verify: record which of three outcomes occurs: denied by the old hook, executed unguarded, or blocked with an error. This is assumption 2.
5. Trust the hook in one scratch repository, then start a session in a second. → verify: the hook runs in the second without a new review (assumption 3).
6. Have the hook log its own working directory and the payload's, and run a command whose working directory differs from the session's. → verify: record both values (assumption 4).
7. Find a way to read hook trust from outside a session: the app-server's `hooks/list` method first, the persisted hook state second. Then disable the trusted hook and read again. → verify: record the exact request and response; whether the read shows the hook as disabled; whether the answer depends on the workspace it is asked for; and how long one read takes, since `kk codex` would do it before every non-interactive launch. Or record that neither mechanism is usable (assumption 7).
8. Put a profile, a base user config and a trusted project config in conflict on one key, and load every baseline key in the profile. → verify: the project value wins and no key is rejected (assumption 5).
9. Place a sub-agent file in `$CODEX_HOME/agents/` and register a hook matcher for an MCP tool. → verify: the agent is available and the matcher fires (assumption 6).
10. Repeat step 1's trust check with the marketplace added from a Git URL. → verify: record any difference from the local source (assumption 10).
11. In a scratch repository, register a project hook whose command runs a script from the repository, the way the legacy registrations in `.codex/hooks.json` do. Trust it, open a session, delete the script, and send a guarded command. → verify: record whether the call proceeds unguarded, is blocked, or fails with an error (assumption 12). This decides the wording of the warning `kk migrate` gives about older sessions.
12. After step 4 has left the guard at its new version, re-add it at the earlier version with the earlier bytes, as a rollback would. → verify: record whether Codex installs an earlier version over a later one, and whether the earlier bytes are still trusted or need review again (assumption 14). Rollback depends on the first; the second decides whether a rollback across a guard change needs the adopter's review.
13. Run `codex --profile <name> -c developer_instructions=…` with a multi-line value of 64 KiB, and again in a trusted project whose `.codex/config.toml` sets its own `developer_instructions`. → verify: record the largest value accepted, on Linux and macOS, and which value the session shows in the second case (assumption 15). `codex debug prompt-input` renders the prompt without a model call. Already observed on 0.169.0: the argument replaces the profile's value, and `@` lines in `AGENTS.md` are not followed.

Update the design's Assumptions and affected sections with each result before closing the task.

## `kk` foundation

Deliver one complete path for Claude: a first install on a clean machine, an upgrade, a rollback and a status report.

**Files to create**

- `kk/bin/kk` — the stable entry point, a short shell script. It resolves the toolbox home, reads the state file, and runs a release's CLI under isolated Python (see [the `kk` command](design.md#the-kk-command)). For `rollback` that is the release being restored: the active release when a candidate is pending in *activating*, the rollback target otherwise. For everything else it is the active release. It contains no upgrade logic. It reads only the active release, the rollback target and the candidate's phase, with `jq`. Because every release ships this file, the copy inside a release directory works as a recovery entry point when the stable one does not.
- `kk/lib/` — the CLI modules. Keep them few: state, payload, validation, Claude activation, command dispatch.
- `kk/payload.json` — the payload's layout version and the directories it must contain.
- `kk/selftest/guard-cases.json` — a small set of guard inputs with expected decisions, covering an allowed command, a secret read, a destructive command and a protected-path edit.
- `install.sh` at the repository root — downloads the latest stable release and runs its upgrade. It must be safe to run again after an interrupted first install. It warns in one line when `kk` on `PATH` resolves to something other than the symlink it installed.
- `test/kk/` and `test/test-kk.sh` — the Python suite and its wrapper.

**Behaviour to implement**

1. Toolbox home resolution and the layout in [Components](design.md#components). Every write is a temporary file followed by a rename. → verify: an interrupted write never leaves a truncated state file (test by failing the rename).
2. The writer lock: `upgrade`, `rollback`, resumption and, once it exists, `apply` hold an exclusive `fcntl.flock` on `$KK_HOME/lock` for their whole run. A second writer exits at once with a message naming the holder. Launchers and `status` do not take it. → verify: with one writer paused mid-activation, a second writer fails without changing the state file or the marketplace manifests.
3. Payload fetch from a tag archive and from a local checkout. Extract only the payload directories. Reject archive members with absolute paths, parent traversal, or symlinks that leave the payload; the plugin contains legitimate relative symlinks. → verify: a crafted archive with each kind of bad member is rejected; a real payload's symlinks survive.
4. A version for local-checkout payloads that cannot collide with a tag.
5. Validation with nothing activated: payload completeness, the guard self-test against the candidate engine, one event through the Claude guard handler as the staged `hooks/hooks.json` registers it (resolve the plugin-root variable to the staged plugin; expect a denial for a secret read and a pass for a harmless command), and `claude plugin validate`. → verify: a candidate with a syntax error in the engine fails validation and leaves the state file unchanged; so does a candidate whose hook registration names a script that is not in the payload.
6. The state machine in [Activation state](design.md#activation-state): one active release, a per-tool state, the rollback target with its fallback to the previously active release, the time each retained release stopped being active, and the installed-paths record. Journal the candidate's phase before each activation step. The file carries a format version. Rewrites are read-modify-write and keep fields the code does not know, because rollback runs an older release's code against a file a newer one wrote. Code refuses a format version it does not know. → verify: a state file with an unknown field keeps it across a rewrite; a file with a higher format version is refused with a message and left untouched.
7. Claude activation: write the local marketplace manifest pointing at the release, add the marketplace and install the plugin on first install, then verify that the matching `claude plugin list --json` entry’s `readFromFolder` resolves to the expected release plugin directory. A missing or mismatched `readFromFolder` fails verification. Marketplace plugin sources must start with `./`. Before writing the `~/.local/bin/kk` symlink, apply the collision rule in [Components](design.md#components): a path that exists and is not in the installed-paths record stops the install. Record the path before writing it. Keep the local marketplace's name in one constant shared by both tools' activation, mixed-install detection and the launcher. Its working value is `toolbox`; the name is an open question the maintainer settles before the first release that ships `kk`.
8. Hand-off: fetch, staging and validation run from the active release's code; activation and verification run from the candidate's. Rollback runs from the code of the release it restores: the active release after an interrupted upgrade, the rollback target otherwise. Status and resumption run from the active release. On a first install there is no active release: the installer runs the staged candidate directly, and a second run resumes from the journaled phase or starts over.
9. `kk rollback` to the rollback target, `kk status`, and pruning. A release is pruned only when it is not active, not the rollback target, and stopped being active more than 14 days ago. `kk upgrade` ends by printing the per-release recovery command.

→ verify: with stub vendor CLIs, the suite covers first install, an interrupted first install completed by running the installer again, upgrade, failed validation, interruption at each activation step followed by resume and by rollback, two overlapping writers, and pruning. The pruning case keeps a release that was active for a month and superseded yesterday. A rollback case promotes a release, makes its `kk/lib` unreadable, and restores the previous one twice: through the stable entry point, and through the copy inside the rollback target after the stable entry point has been broken too.

### Running the Claude first-install increment

From this checkout, `./install.sh --local .` installs the working tree. `~/.local/bin/kk status` shows the promoted release and Claude’s state. If installation stops partway, run the installer again. It verifies the journaled candidate, resumes an intact copy locally and rebuilds an incomplete copy from its recorded source. `KK_HOME` selects the toolbox directory. The stable symlink lives in `~/.local/bin/`.

With no source argument, a fresh install selects the latest stable GitHub release. `--version vX.Y.Z` selects a tag and `KK_REPOSITORY=owner/repo` selects a fork. A tag needs to contain this installer and the declared payload. The marketplace name must be settled before publishing the first such tag. Task 3 requires the three directories in `kk/payload.json`. Task 7 adds the fourth when it creates the Codex guard.

## Migration

Migration is two steps run by `kk migrate`: an ordinary sync to the retirement release, then removal against that release's template. The removal logic goes into the sync script as a separate mode, `--retire`. It does not follow the `needs_*` / `run_*` migration pattern. Those migrations run from `apply_changes`, which a local `--local` sync and the downstream workflow's `--apply` both reach, and neither can check that a replacement guard works. The rules are in [Removal rules](design.md#removal-rules); the reasons for the separate mode and the tombstone are in [Ordinary sync and the tombstone](design.md#ordinary-sync-and-the-tombstone).

1. Add `--retire` to `parse_arguments` and a retirement path in `main` that runs only when the flag is given, with `--version` naming the retirement tag. With `--dry-run` it previews; without, it applies. It fetches the template at that tag with `fetch_upstream_templates` and renders it the way a first-time sync does: manifest substitutions applied, nothing merged in from the repository. No other mode calls the removal functions. In every existing mode, a run of this release prints one notice naming `kk migrate` and otherwise behaves as before. → verify: one fixture run three ways. `--local` and a staged `--apply` leave every guard file and hook registration in place; `--retire` removes them. Run directly against a repository that was not synced first, `--retire` keeps and reports every file and entry that differs from the template; it is never less safe than the two-step run, only less complete.
2. Add the deny-merge switch for the sync step. When `TEMPLATE_SYNC_MERGE_DENY=1` is set, `apply_substitutions` leaves `permissions.deny` out of `owned_paths` and skips the assignment of the upstream deny list after the merge, so the merge's existing array rules apply to it. Only `kk migrate` sets the variable. → verify: with it, a sync keeps a deny entry the repository added and removes one the template retired since the base; without it, the sync behaves exactly as today. Without a settings base the merge is a union, so an entry the template retired stays and is later kept by removal; the report lists it.
3. Hook registrations: remove from the repository's hooks file each handler whose command string equals a toolbox handler in the rendered template. Drop groups and events that become empty. Leave every other handler. This replaces the group-level substring filter for this purpose.
4. Settings and Codex config: a removal-only comparison against the rendered template. Do not call the three-way merge in `apply_substitutions`.
   - Remove an entry when it equals the template's. For `permissions.deny`, remove only the entries the template's deny list contains.
   - Keep `sandbox_mode`, `approval_policy` and `approvals_reviewer` in the Codex config whatever their values, and list them in the report. Nothing on the machine replaces them by default.
   - Keep the keys the manifest controls (`model`, `effortLevel` and `permissions.defaultMode` in the Claude settings; `model` in the Codex config) when the manifest holds a value other than the script's built-in default, and list them in the report as the adopter's choices. Remove them otherwise. Remove `statusLine` and list the manifest's statusline choice.
   - Remove the Git-marketplace plugin enablement and marketplace registration.
5. Files: remove synced files identical to the rendered template. Report files that still differ and keep them. Remove the two toolbox import lines from the project instructions file when they match exactly.
6. Skip every path matched by `sync_exclusions`, in steps 3 to 5, and list what was skipped.
7. Stop without removing anything when the template cannot be fetched.
8. Remove the sync infrastructure last.
9. The report states the team-wide effect in the words of [What `kk migrate` does](design.md#what-kk-migrate-does). It lists the kept Codex sandbox and approval settings, says that they keep outranking each machine's Codex config in this repository, and names the three lines to delete to hand that over to the machine. It lists the kept manifest choices with the same note about the machine defaults. It also lists every `.claude/CLAUDE.<name>.md` other than the toolbox's own and says that Codex will stop receiving it unless the repository adds an `@` line for it to `AGENTS.md`.
10. Write the tombstone that replaces the script after retirement, in this task so that it is tested before it is needed. It accepts every option the script has accepted, sources nothing, changes nothing, prints the migration guidance, and exits successfully. With `--ci` it writes `has_changes=false` to the workflow output so no pull request is opened. → verify: the previous release's script, run with `--local` against a fixture upstream that holds the tombstone, hands over and leaves the working tree unchanged apart from the manifest fields that script backfills before handing over; the same for a staged `--apply`.
11. `kk migrate`:
    - check for `curl` and Mike Farah's `yq`, and say they are needed for this step only;
    - for each tool the repository uses, read trust and enablement with the trust reader, for this repository when the mechanism takes a workspace, and run `kk status --live` as it is, in its scratch workspace; refuse unless the guard's own denial is seen;
    - state the warning about Codex sessions opened before `kk` was installed, worded from the result of the deleted-script probe, and ask, default no;
    - fetch `template-sync.sh` and `semver-compare.sh` from the retirement tag into a temporary directory. Without the helper beside it, the script fetches one from the default branch, where it will no longer exist. The tag is a constant in `kk`; `--retirement-version` overrides it for the pilot. If the retirement script needs a fix after the template is retired, cut a patch tag from a branch at the retirement tag and move the constant to it in the next `kk` release;
    - sync step: run the script from there with `TEMPLATE_SYNC_NO_HANDOFF=1`, `TEMPLATE_SYNC_MERGE_DENY=1` and `--dry-run --version <tag>`; if it reports changes, show them, ask, and run `--local --version <tag>` with the same variables;
    - removal step: run `--retire --dry-run --version <tag>`, ask, run `--retire --version <tag>`;
    - leave the changes uncommitted. Declining the removal step leaves the repository synced and guarded.

→ verify: fixtures in `test/test-template-sync.sh` for a repository with capy's hooks, an adopter-added hook, a customised settings file, a deny entry the template never shipped, a manifest that selects a Claude model and a Codex model, a Codex config still holding the template's sandbox and approval settings (kept), an edited synced file (overwritten by the sync step and shown in its preview), an edited file under `sync_exclusions` (untouched by both steps), and a repository several releases behind, which must end in the same state as one that was up to date. Every non-toolbox entry survives byte for byte. → verify: record the third demonstration on one of the maintainer's repositories, with a Codex session opened before `kk` was installed.
