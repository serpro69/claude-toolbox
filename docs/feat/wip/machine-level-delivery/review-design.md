# Design review of machine-level delivery

Reviewed 2026-11-18 against repository revision `9c6bd133`. Scope covers the [design](design.md), [implementation plan](implementation.md) and [tasks](tasks.md).

**Assessment — MAJOR_GAPS.** Moving release delivery to the adopter’s machine is worth pursuing. One update per machine directly addresses the seven-repository maintenance cost. Keeping recovery outside the vendor plugins and separating the Codex guard from frequently changing skills both have a concrete purpose. I would proceed with the vendor probes and a pilot, and hold the retirement release.

The main product decision is what installing `kk` authorizes across the account. Shared release files, defaults selected when running a launcher, and a mandatory rule in every bare Codex session have different effects. Decide which of these the adopter wants before investing in the rest of the installer.

A command that refreshed all seven existing checkouts would reduce the maintainer’s repetitive work. It would still write into repositories, leave new clones needing setup and retain the sync engine. The zero-setup requirement for new repositories is what justifies changing the delivery model. For existing repositories, the one-command promise starts after the one-time migration. Until then an old project model, statusline or approval setting can continue to outrank the new machine default even in a wrapped session. [Success measures](design.md#success-measures) · [Legacy coexistence](design.md#legacy-coexistence-and-migration)

## P0 — Critical

1. **An ordinary sync can retire a repository without checking its replacement guard.** The plan makes a retirement marker and `APPLY_MODE` sufficient inside the sync script. Both a normal `--local` sync and the existing workflow’s apply phase use that mode. The local path even hands off to the fetched script before comparison. A user asking for the latest template can therefore enter the removal path without the readiness check and consent in `kk migrate`. Give retirement its own explicit invocation. Ordinary sync against the retirement tag should explain how to migrate and preserve the legacy installation. Exercise both entry points against the same fixture. **TECH_RISK · confidence 10/10** from the two current callers. [Task 13](tasks.md#task-13-retirement-migration-in-the-sync-script) · [Sync script](../../../../.claude/toolbox/scripts/template-sync.sh) · [Downstream workflow](../../../../.github/workflows/template-sync.yml)

2. **A release that reaches ready takes control of its own rollback.** After B passes activation, B is the “last ready” release and can replace `bin/kk`. A regression confined to B’s command dispatcher or rollback can strand the machine even with A intact on disk. An interrupted first install has the reverse problem. No last-ready release exists. Keep a small, independently invocable recovery path that can restore A without importing B, and define how the bootstrap resumes or cleans up the first install. Demonstrate offline recovery *after* promotion with B’s normal CLI unavailable. The planned interruption test exercises a different failure. **TECH_RISK · confidence 10/10** from the dispatch and promotion order. [Command dispatch](design.md#the-kk-command) · [Activation](design.md#upgrade-flow) · [Task 4](tasks.md#task-4-upgrade-rollback-and-recovery-for-claude)

## P1 — High

3. **Recorded readiness can outlive effective hook trust.** The launcher consults its journal before a headless run, and migration consults the same state before removing the old guard. Codex lets the operator disable an individual hook after activation. The proposed fallback also lets an acknowledgement end “awaiting review” when trust could never be observed. Either path can authorize migration or an unattended session with an inactive replacement. At those decision points, check the enabled, trusted handlers for the selected plugin and workspace. Keep an unverified result distinct from ready. Use the planned live check where invocation evidence is needed, with evidence attributable to the installed handler. **TECH_RISK · confidence 9/10**. The mismatch holds even though the exact vendor query still needs probing. [Trust tracking](implementation.md#codex-activation-and-trust) · [Migration prerequisite](design.md#legacy-coexistence-and-migration) · [Codex hook trust](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)

4. **Migration can remove the only guard an already-open session loaded.** A Codex process started before machine installation can hold only the legacy registration. Its handler invokes a script from the repository on each call. A fresh session can pass the replacement check while migration deletes the script the older session still needs. Task 14 should include a session opened *before* installation. Either preserve the required files for the handover or require affected sessions to close and restart, and scope the continuity claim accordingly. **TECH_RISK · confidence 9/10**. The legacy paths are explicit. The old process’s response to their removal is a vendor-probe question. [Continuity demonstration](design.md#verification) · [Task 14](tasks.md#task-14-kk-migrate-and-the-migration-demonstration) · [Legacy registrations](../../../../.codex/hooks.json)

5. **Two writers can produce an installation described by neither journal.** A scheduled upgrade and a manual rollback can interleave marketplace writes, vendor installs and profile replacement. Atomic rename keeps each file readable, but the last journal writer can record a different release from the installed guard. Use one writer lock for activation, rollback and resumption. Define which release each tool actually runs while Claude is ready on B and Codex awaits review on B, and retain every release needed for that state. One overlap test and one mixed-tool recovery case are sufficient. **TECH_RISK · confidence 9/10** from the shared files and explicitly supported scheduler. [State model](design.md#activation-state) · [Upgrade sequence](design.md#upgrade-flow) · [Scheduled upgrades](design.md#not-doing)

6. **The existing settings merger cannot perform the promised lossless retirement.** It assigns the entire Claude deny list from upstream after the three-way merge and then reapplies manifest-owned settings. Empty upstream denies can erase a downstream-only deny. Comparing against a template rendered with the adopter’s manifest can also classify an explicitly chosen project model or approval policy as disposable. Give retirement a removal-only comparison against the recorded base, preserve exclusions and adopter choices, and keep ambiguous values when the base is unavailable. Include a downstream-only deny and a manifest-selected project preference in the migration fixture. **INCONSISTENT · confidence 10/10** from the merge assignment and substitution code. [Removal contract](design.md#legacy-coexistence-and-migration) · [Existing merger](../../../../.claude/toolbox/scripts/template-sync.sh) · [Meaning of manifest choices](../../../user-guide/template-sync.md)

7. **A reserved-looking filename does not establish ownership.** The plan writes `~/.local/bin/kk`, `kk.config.toml`, `rules/kk.rules` and prefixed agent files in directories shared with the adopter. On first install those paths may already belong to someone else. A broad prefix also cannot identify obsolete files safely. Check the destinations before activation, report a collision without replacing it, and prune only exact paths recorded as installed by `kk`. Include one pre-existing file and one unrelated prefixed agent. **MISSING · confidence 9/10** from the ownership constraint and the installation/pruning contract. [Machine layout](design.md#components) · [Owned file installation](implementation.md#codex-baseline-and-launch)

8. **A guard version does not identify its bytes for every supported source.** A local checkout may change the guard with the published manifest version intact. Task 10 then skips installation, or detects the tree mismatch only after other machine files have changed. Conversely, comparing each release candidate with the previous *stable* tag can assign two guard versions to identical bytes on the RC-to-stable path, causing needless reinstallation and review. Define guard identity from the actual bundle contents across stable tags, prereleases and checkouts. Preflight a same-ID/different-content conflict. Use the resulting identity consistently for installation, confirmation and rollback. **INCONSISTENT · confidence 9/10** from the local-source and versioning rules. [Supported payloads](design.md#release-payload) · [Activation](implementation.md#codex-activation-and-trust) · [Release version rule](implementation.md#ci-gate-and-release-workflow)

9. **The parity ledger understates the Codex policy change.** Moving native forbids into `$CODEX_HOME/rules/` imposes them on bare Codex in unrelated repositories. A repository that deliberately excluded the template’s native rules loses that choice. The existing file forbids even ordinary `rm`, and a project allow cannot loosen it. Separately, the wrapped profile selects approval and sandbox settings above the adopter’s base config. Record both as product decisions. My preference is to preserve the machine owner’s approval and sandbox choices by default and make account-wide native forbids an explicit install choice. If global enforcement is a requirement, show the effect before installation and state which existing per-project controls are lost. **TECH_RISK · confidence 10/10** from the current rules, documented exclusion and profile precedence. [Parity ledger](design.md#parity-ledger) · [Native rules](../../../../.codex/rules/default.rules) · [Existing project control](../../../providers/codex.md#permission-guard) · [Codex profile precedence](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles)

10. **The Claude pass-through drops a promised protection.** `kk claude --settings …` starts Claude without the toolbox layer. After migration an ordinary adopter settings file can therefore leave a wrapped session without the native denies. Applying arbitrary named overrides last also leaves the fate of generated denies ambiguous. Specify the result for both paths. Compose the mandatory entries with supported overrides, or explicitly label pass-through as an unmanaged launch and narrow the parity claim. Check the effective deny with hooks disabled, as the existing probe proposes. **INCONSISTENT · confidence 10/10** from the launch and protection contracts. [Claude launcher](design.md#launching-claude) · [Overrides](design.md#overrides) · [Protection guarantee](design.md#protection-guarantee)

11. **The preflight can pass without exercising the component it is about to install.** A valid but incomplete candidate `kk.rules` can pass the known-forbidden-command check when another file supplies the same forbid. Testing the Python engine directly also leaves a mispackaged Codex adapter or an incorrect hook registration outside that check. Check the candidate rule on its own, then parse the combined set for compatibility. Send a representative event through the handler named in the staged manifest. This gives a local claim about the packaged guard before activation, while live trust and dispatch remain vendor checks. **TECH_RISK · confidence 9/10** from the documented preflight inputs and the separate adapter entry points. ## Decision and verification

Keep the immutable local release, the separate Codex guard pending its probe, and one adopter-run upgrade. These choices support offline rollback and avoid making frequent skill edits a reason to review trusted code. The proposed long-lived TUI probe can settle whether the same process still invokes that guard after a skills update.

Move the decisive part of Task 17 ahead of Task 16. Pilot the actual tagged payload on a clean install and on one legacy repository. Use the existing demonstrations to cover a skills-only upgrade, recovery from an interrupted and a promoted release, and migration with a pre-existing session. Demonstrate that ordinary template sync leaves the legacy guard intact. A scratch marker plugin can settle vendor mechanics early. The shipped adapters, marketplace identities and migration entry points should determine whether it is time to retire the template. [Verification goals](design.md#verification) · [Retirement and final verification](tasks.md#task-16-retire-the-template-in-this-repository)

The installed CLI versions matched the design’s stated baseline of Claude Code 2.1.296 and Codex 0.169.0. This review checked repository behavior, CLI help and vendor documentation. Live installation, trust, cache replacement and open-session behavior remain evidence for the pilot.
